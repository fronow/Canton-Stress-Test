Contention isn't a concurrency effect. It's a bookkeeping effect.

A random pick fails when it lands on a holding the wallet already spent. The spent fraction grows from 0 to f over a run, so the average failure rate should be about f/2 — and it should not care how many submissions are in flight. Predictions were fixed before the runs.

contention ≈ f / 2  where f = holdings spent ÷ pool size

Raising concurrency 4x, from 8 to 32, at the same pool depth. If contention were a collision-between-concurrent-submissions effect, this should have moved sharply. It didn't.

And it is avoidable entirely
12.5% → 0%

Handing each in-flight submission a distinct holding — a per-submission reservation — removes contention completely, at every concurrency tested, with no latency cost.

Where the model is weakest

It under-predicts at high turnover (37.1% vs 31.5%), which is where genuine concurrent collisions add on top. Treat it as a floor and a good estimate, not an identity.
